# 第三章、消息最常用的元数据字段

## 1、对象格式消息最常用的元数据字段

注意：Json格式和对象格式都支持元数据字段，这里以对象消息为例。

## name 字段

**主要使用场景：**

- **多角色区分**：在多 Agent 协作或对话中有多个不同角色的系统/用户消息时，通过 `name` 来标识具体的消息来源或角色名称。
- **模型适配**：部分底层大模型（例如 OpenAI 的 Messages API）原生支持为特定 Role 传递 `name` 字段，LangChain 会将该属性透传给底层模型 API。

```bash
from langchain_core.messages import SystemMessage, HumanMessage

system_msg = SystemMessage(
    content="你是一个专业的代码审查助手。", 
    name="system_reviewer"    # 消息的name元数据字段
)

# HumanMessage
human_msg = HumanMessage(
    content="请帮我检查一下这段代码。", 
    name="user_alice"    # 消息的name元数据字段
)
```

## id 字段

在 LangChain 中，`id` 用于唯一标识一条消息（通常为字符串格式），方便在消息追踪、数据库/缓存持久化（如 `ChatMessageHistory`）以及更新或过滤特定消息时进行精确定位。

```bash
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

# 手动指定消息 id
system_msg = SystemMessage(
    content="你是一个专业的代码审查助手。", 
    id="sys_001"
)

human_msg = HumanMessage(
    content="请帮我检查一下这段代码。", 
    id="msg_001"
)

ai_msg = AIMessage(
    content="好的，请把代码发给我。", 
    id="msg_002"
)
```

# 2、实际案例

## 2.1、SystemMessage上元数据的实际用法

在 `SystemMessage`（系统消息）上设置 `name` 和 `id` 等元数据，虽然不像在普通消息上那么频繁，但在**复杂对话管理、多 Agent 架构**以及**模型特定适配**中有着至关重要的实际作用。

### **name 在**SystemMessage消息中**的实际作用：多 Agent / 多系统指令标识**

许多底层大模型（如 OpenAI 的 Chat Completion API）原生支持在 system 角色中传入 name 字段。当在一个复合应用或多 Agent 框架中，存在多个针对不同任务的系统提示词（System Prompt）时，name 用于明确区分当前系统指令是由哪个模块或子系统发出的。

#### 实际案例：带审查功能的客服 Agent

在这个例子中，主回答 Agent 和安全审查 Agent 可能会分别插入一条 `SystemMessage`。通过 `name` 区分它们，模型或后端日志就能清晰分辨指令来源。

```python
from langchain.chat_models import init_chat_model
from dotenv import load_dotenv
from langchain_core.messages import SystemMessage, HumanMessage

load_dotenv(override=True)

llm = init_chat_model (
    model = "gpt-4o-mini",
    model_provider = "openai"
)

# 1. 业务主逻辑的系统指令
core_system = SystemMessage(
    content="你是一个电商平台的售前客服，回答需礼貌且简短。",
    name="customer_service_agent"
)

# 2. 安全合规模块动态注入的系统指令
guardrail_system = SystemMessage(
    content="严禁向用户提供任何未公开的内部优惠码或财务敏感数据。",
    name="compliance_guardrail"
)

# 发送给 LLM 时，OpenAI API 会接收到 name="customer_service_agent" 和 name="compliance_guardrail"
# 这样不仅能约束模型行为，在 LangSmith 等链路追踪工具中也能精准辨识是哪套 Prompt 生效了。
messages = [
    core_system,
    guardrail_system,
    HumanMessage(content="你们有没有内部员工折扣码？")
]

response = llm.invoke(messages)
print(response.content)
```

### **id 在**SystemMessage消息中**的实际作用：动态替换与更新 System Prompt**

在长对话或状态图框架（如 **LangGraph**）中，系统提示词并不是一成不变的。例如，随着用户引导流程（Onboarding）的推进，或者用户身份切换（如从“普通用户”升级为“VIP用户”），我们需要**实时更新对话历史中的 `SystemMessage`**，而不能直接追加一条新的 `SystemMessage` 导致指令冲突。

通过固定的 `id`，我们可以精准定位并覆盖/更新原有的系统消息。

#### **实际案例：动态更新系统状态/指令**

```python
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

# 定义一个固定的 system id
SYSTEM_MSG_ID = "main_system_prompt"

# 初始对话状态：用户处于试用阶段
messages_history = [
    SystemMessage(
        content="当前用户身份：【试用用户】。如果用户询问高级功能，请提示其升级套餐。", 
        id=SYSTEM_MSG_ID
    ),
    HumanMessage(content="怎么导出 PDF 报告？"),
    AIMessage(content="导出 PDF 是高级功能，请升级套餐后使用。")
]

# ... 触发事件：用户在后台成功完成了充值/升级 ...

# 当我们需要更新 SystemMessage 时，只需创建一个相同 id 的新 SystemMessage
updated_system_msg = SystemMessage(
    content="当前用户身份：【VIP用户】。用户已解锁所有功能，请积极解答其高级功能的使用方法。",
    id=SYSTEM_MSG_ID
)

# 在支持 id 覆盖的消息列表中（如 LangGraph 的 add_messages 状态更新器），
# 传入相同 id 的消息会自动“替换”掉原来的 SystemMessage，而不是追加在末尾：
# 结果：messages_history[0] 被替换为新的 updated_system_msg
```

## 2.2、HumanMessage上元数据的实际用法

在 `HumanMessage`（用户消息）上使用元数据，主要围绕**多用户身份辨识**、**消息追踪与流转**以及**前端交互同步**展开。

### name在HumanMessage消息中的实际作用：多用户群聊与多 Agent 对话

#### 实际案例：多人会议/群聊助手

在这个场景中，AI 助手需要根据不同的发言人做出针对性的回复或总结。

```python
from langchain_core.messages import SystemMessage, HumanMessage

messages = [
    SystemMessage(content="你是一个会议记录助手，请根据发言人回答问题。"),
    
    # 通过 name 区分不同的真实用户
    HumanMessage(content="我认为这周应该优先上线支付功能。", name="Alice"),
    HumanMessage(content="但是支付模块的测试还没做完，风险太大。", name="Bob"),
    
    # 提问时明确指定了具体人名
    HumanMessage(content="总结一下 Alice 和 Bob 的核心分歧是什么？", name="Charlie")
]
```

### id 在HumanMessage消息中的实际作用：前端消息同步与交互修改

在实际的 Web UI（如 Chatbot 界面）中，前端通常会为用户发送的每一条消息生成一个唯一的客户端 UUID（或者后端存库时生成自增/UUID 主键）。`id` 字段是**关联前端 UI 与后端 LLM 状态**的关键桥梁。

#### 实际案例：用户“编辑并重新发送”消息（如 LangGraph 状态覆盖）

当用户在前端点击“编辑”按钮修改了上一条发送的消息时，后端需要使用相同的 `id` 覆盖掉原有的 `HumanMessage`，以避免历史记录重复。

```python
from langchain_core.messages import HumanMessage, AIMessage

# 用户发送了第一版消息，前端赋予 id="msg_user_9981"
history = [
    HumanMessage(content="帮我写一段 Python 快速排序代码", id="msg_user_9981"),
    AIMessage(content="好的，这是快速排序的代码...")
]

# 用户在前端点击了“编辑”，把提问改成了“用 Go 语言写”
# 后端接收到请求后，创建相同 id 的 HumanMessage 进行状态覆盖/更新
edited_human_msg = HumanMessage(
    content="帮我写一段 Go 语言快速排序代码", 
    id="msg_user_9981" # 相同的 id，用于在数据库或 LangGraph 中覆盖旧消息
)
```
